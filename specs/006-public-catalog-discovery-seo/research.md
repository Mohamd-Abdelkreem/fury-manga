# P05 Technical Research

Technical choices are resolved for planning. The home-suggestion selection is fixed under the owner's instruction to resolve the outstanding P05 decision. The owner accepted the written requirements review and authorized isolated synthetic-data P05 development on 2026-09-27; prerequisite phase exits remain separate release gates in `plan.md`.

## Request-time public reads and SEO

**Decision:** Render P05 route content and work metadata from a request-time, credential-free server read using native `fetch` with `cache: "no-store"`; mark affected Next route segments and the sitemap dynamic. Keep browser interactions on the existing central Axios client and React Query. Validate every response with shared contracts. Use a validated, owner-configured public site origin for canonical URLs; never derive it from `Host`.

**Evidence and rationale:** `apps/web/src/services/api/api-client.ts` has a module-level access token, `withCredentials`, and refresh/redirect interceptors, so importing it into a server component could cross request identity and would give crawlers session-sensitive behavior. Installed Next 16 guidance at `apps/web/node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`, `01-app/03-api-reference/04-functions/fetch.md`, `01-app/03-api-reference/04-functions/generate-metadata.md`, and `01-app/03-api-reference/03-file-conventions/01-metadata/sitemap.md` establishes the request-time fetch, server metadata, and special-route caching behavior. Public publication changes must affect new page and crawler reads. The server fetch is a small request-isolated boundary, not another browser API/session stack. `NEXT_PUBLIC_API_URL` is build-inlined; a server-only API origin may be configured separately for deployment routing, while public image URLs and canonical links must remain externally reachable.

**Alternatives rejected:** Static generation or timed revalidation can advertise withdrawn works after a new request. The browser client in server code carries ambient session state. A second browser HTTP client would duplicate auth/error ownership. Request `Host` is not a trusted canonical origin.

## Public contract evolution

**Decision:** Add P05 catalog-specific read routes in the existing content module, sharing its public eligibility policy, service, query owner, response envelope, and error protocol. Register static catalog paths before the work-slug route. Keep the four existing public work/chapter metadata routes wire-compatible. The rich catalog output is a new shared Zod contract, not an expanded response on the old strict DTO. List success preserves the existing response helper's optional top-level `paginationMeta` equal to the nested pagination; nonlist success omits it. Parsed schema failures retain `400 VALIDATION_ERROR` with field paths; malformed percent encoding rejected before parsed validation uses `400 BAD_REQUEST` without a false field path. Use the existing chapter-summary route for later chapter pages. Set `Cache-Control: no-store` for existing and new public content GETs at an early path-scoped boundary after request ID and before CORS, body parsing and the existing limiter so 429, validation, other failure and success responses are covered without reordering existing middleware.

**Evidence and rationale:** `packages/contracts/src/content/content.schema.ts` defines strict public work output; extending the existing response would break independently deployed strict parsers. `apps/api/src/modules/content/content.routes.ts` already separates anonymous content reads from authenticated ADMIN commands. `apps/api/src/modules/content/content.queries.ts` has `PUBLIC_READY_WORK_WHERE` and ready-chapter SQL; `public-content.service.ts` uses repeatable-read snapshots for list/count. `ResponseHelper` adds `paginationMeta` for list data with top-level pagination. `apps/api/src/app.ts` installs the global API limiter before the content router, so a route-local header would miss limiter failures. One feature-local service/query implementation can serve old and new projections without another content lifecycle.

**Alternatives rejected:** Mutating the old strict DTO is a compatibility break. A separate catalog backend or database projection creates duplicate visibility authority. Reading all work records into the web app to filter locally leaks scope and makes totals/pagination wrong.

The existing request sanitizer retains ordinary query values and malformed URL text, while final not-found messages include an unknown raw path. P05 search and malformed/unknown-path privacy therefore needs a scoped projection that logs request ID, method and safe route identity while excluding search terms and raw path/query values. Reuse the existing logger and safe-error/not-found boundaries; prove the final emitted log and error envelope with sentinel values rather than assuming a parsed validation error is sufficient.

## Public cover and background delivery

**Decision:** Add anonymous, work-slug-scoped image reads under public content routes. Recheck current public work eligibility and the active, correctly classed available asset reference before reading bytes. Reuse the existing storage integrity behavior; return safe image bytes with `nosniff` and `Cache-Control: no-store`. Unknown/nonpublic work or absent optional background gives `404 NOT_FOUND`; failure reading bytes while the saved asset remains `AVAILABLE` gives `503 MEDIA_UNAVAILABLE` and does not change work eligibility. Only a committed `UNAVAILABLE` asset state removes the work from subsequent public reads; verified restoration can make it eligible again. Preserve the authenticated `/media` router.

**Evidence and rationale:** `apps/api/src/modules/media/media.routes.ts` authenticates every media route. `media.service.ts` checks bytes against saved length and SHA-256 and maps storage failure to a safe error. `content.queries.ts` already requires an available ADMIN `WORK_COVER` for public eligibility. Existing media reference uniqueness and publication constraints are in forward migrations under `packages/database/prisma/migrations/`. A work-scoped URL exposes no asset UUID or storage path and can be invalidated by publication/category/media changes.

**Alternatives rejected:** Making `/media/assets/:assetId/content` public would bypass the work's current publication decision and expose other media classes. A permanent public file URL would outlive unpublication. Turning a storage failure into 404 would falsely confirm absence; exposing the storage error would leak internals.

## Persistence and catalog ordering

**Decision:** Reuse the existing Work, Category, Chapter, MediaAsset, MediaReference, and PublicationEvent model with read-only queries and deterministic unique tie-breakers. No correctness migration or `data-model.md` is planned. Keep catalog and chapter reads bounded; assemble the complete sitemap slug set from bounded keyset batches inside one repeatable-read transaction so a sitemap response has one visibility snapshot. Examine representative PostgreSQL query plans for latest-release and chapter-publication sorts before adding an index. If evidence warrants one, amend this plan and use only a new forward migration with fresh and upgraded database tests.

**Evidence and rationale:** `schema.prisma` already has immutable unique work/category slugs, unique chapter number per work, category position/order, work publication and chapter-by-work indexes. `20260925010000_p03_editorial_foundation/migration.sql` also has a partial unique published-feature-order index. There is no global chapter-publication-time index, but the roadmap gives no traffic or latency target that proves its necessity. Read responses can use repeatable-read transactions to keep each list/count/composite response coherent. Public requests have no write, idempotency key, deletion, or external side effect.

**Alternatives rejected:** A new catalog table or materialized copy adds consistency and migration risk. A speculative index has write/storage cost without measured benefit. Unbounded in-memory filtering or offset traversal without a unique tie-breaker is not acceptable. Independent HTTP cursor requests would yield a mixed sitemap under concurrent unpublication.
