# P04 Data Model and Invariants

This design evolves the existing Prisma/PostgreSQL content and P02 media models. It does not rewrite the applied P01/P02 migrations or generated Prisma output. [Research](research.md) records the tradeoffs; [HTTP contract](contracts/chapter-http.md) defines the wire representation.

## Entities and relationships

| Entity                                 | P04 fields and meaning                                                                                                                                                                                                     | Relationship and retention                                                                                                                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Work                                   | Existing ID, type, publication state, eligibility. Authoritative source of Chapter content type.                                                                                                                           | One Work has many Chapters. Work deletion remains restricted by Chapters.                                                                                                                              |
| Chapter                                | Existing UUID, Work ID, unique positive whole number, type, nullable structured text, state, published timestamp, current publication-event ID, version/timestamps. Add required normalized title, at most 200 characters. | Stable ID and Work parent. No Chapter hard delete. Legacy title is nullable only during a guarded migration stage, never in the final authoring/public contract.                                       |
| ChapterPage                            | Existing UUID, Chapter ID, positive position, creation time. Add retirement time to distinguish current pages from retained historical pages.                                                                              | Active page has exactly one active `chapter_page` media reference in a complete illustrated Chapter. Retired rows retain identity and references/events; public/admin active projections exclude them. |
| MediaAsset                             | Existing private admin-scoped `chapter_page` class, upload attempt and AVAILABLE/UNAVAILABLE state.                                                                                                                        | Candidate may remain unbound. Active references prevent removal under P02 retention rules. A later unavailable state changes public eligibility without changing publication history.                  |
| MediaReference and MediaReferenceEvent | Existing active/retired Chapter-page association, reference version, and immutable bind/replace/retire events.                                                                                                             | Exactly one active reference per active Chapter page; at most one enforced by the existing partial unique index. Association changes retain events and old asset identity.                             |
| PublicationEvent                       | Existing immutable event ID/time and Chapter link.                                                                                                                                                                         | One new event for each actual transition into published; `currentPublicationEventId` points to current publication and is cleared on unpublish/archive. Historic events remain.                        |
| Structured document                    | JSON version `1`, 1–500 blocks when present, at most 512 KiB serialized.                                                                                                                                                   | Null means incomplete private text draft/archived Chapter. A published text Chapter has a nonempty validated document.                                                                                 |

## Storage constraints and indexes

- Retain `UNIQUE (work_id, number)`, positive number check/bound, Work and Chapter foreign keys, Chapter version, status/timestamp consistency, and publication event relationships. Add title not-blank/length and normalized-write validation; the final non-null constraint follows legacy remediation.
- Existing `UNIQUE (chapter_id, position)` covers all pages and prevents swaps with retired history. Forward-migrate it to a partial unique active-page index (`retired_at IS NULL`) and retain a positive-position check. Use collision-safe staged updates (or a suitable deferred database strategy) during reorder; validate final consecutive `1..N` positions at the service and commit boundary. Retired rows keep their last position for audit and cannot be selected as active.
- Add active-page query index keyed by Chapter, retirement, position, and ID. Keep media active-reference uniqueness and FKs; verify a committed complete/published illustrated Chapter has an active valid reference for every active page. Use a deferred constraint/trigger where cross-row commit-time protection is needed, with the service performing the same validation for field-level errors.
- Permit null text only for draft/archived text Chapters. Preserve the illustrated-null-text rule. Strengthen published readiness checks to require title and nonempty valid text or an active illustrated page set with required references. Media availability is checked at publish/update and public read, because later reconciliation can legitimately change it without a Chapter transaction.
- List orders append Chapter ID as a tie breaker. Search/title/status/count indexes follow measured query plans; do not add speculative indexes. All list reads are bounded by shared pagination defaults/maxima.

## State transitions

| From      | To                | Result                                                                                                                                |
| --------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| draft     | published         | Require complete type-correct content and available associated media; create one event, set timestamp/current event, advance version. |
| draft     | archived          | Preserve body/pages/history privately; advance version.                                                                               |
| published | draft or archived | Clear current public publication identity/time, preserve historical event and editorial data; advance version.                        |
| archived  | draft             | Restore private draft; advance version.                                                                                               |
| published | published         | Idempotent same-state response with current identity and `transitioned: false`; no new event or version change.                       |
| archived  | published, any    | Reject any other edge or hard delete with a stable safe error.                                                                        |

Same-state retry with a stale `expectedVersion` must resolve against authoritative current state only when it is truly the requested state; otherwise return stale conflict. An edit of a published Chapter may not leave it incomplete. A draft may save incomplete content and reports that readiness truthfully in the admin UI.

## Transaction and race model

1. Validate strict contract bounds; authorize active, verified ADMIN before private lookup. Load parent Work and assert type and Work/Chapter pairing.
2. For update/publication, lock the Chapter and compare `expectedVersion`. For create, the Work-scoped unique number constraint arbitrates concurrent duplicate numbers. Lock selected asset rows in sorted ID order, then existing page/reference rows in deterministic order. Use the established bounded Serializable retry mechanism for database serialization conflicts; exhausted retries become a safe 409.
3. Validate the entire proposed ordered page set: max 500, distinct stable IDs from this Chapter, available admin `chapter_page` assets, no foreign/retired page IDs or incomplete upload, and exactly one consecutive final position. The same accepted asset may serve more than one page unless a future requirement forbids it. Apply page additions, collision-safe position changes, replacement/retirement of active media references with events, and page retirement in one transaction. Advance Chapter version exactly once. A failed validation, FK/check/unique conflict, or injected mid-save failure rolls back every Chapter/page/reference/event change. External candidate upload occurs before this transaction and is not rolled back; unbound candidates remain private and recoverable under P02 rules.
4. Publication takes the same Chapter lock and validates current page/reference/media readiness before one event insert. A competing edit, publish, media removal, or reference change has one serial winner. Asset rows serialize availability-sensitive updates with publication/edit checks. Direct generic Chapter-page reference writes cease at P04 cutover.
5. Public Work/Chapter visibility uses one predicate in list, detail, and count, with a consistent parent/list/count snapshot. `published` state and event history remain when reconciliation marks an asset unavailable. Verified media repair restores eligibility without an event. Physical media may fail before reconciliation updates status; private byte delivery fails closed and operational checks must reconcile before declaring content healthy.

## Forward migration, cutover, and recovery

1. **Preflight:** On a backup/restore-tested copy of the last accepted P01–P03 state, inventory Chapter count, missing titles, published text validity, published illustrated pages without exactly one accepted available image, duplicate or nonconsecutive active positions, existing media references, and publication-event links. Capture IDs for operator remediation; do not invent titles/images or erase events. Record baseline, migration versions, and the approved maintenance/old-client write cutoff. Stop if P02/P03 dependency exit gates are unaccepted.
2. **Expand-only release:** Package and apply only the new expand migration, which adds nullable title and page retirement state, changes the text draft check, and prepares active-page indexes/constraints without rewriting applied history. Keep the last compatible public title-free API projection during this interval. Block independent old editorial clients from Chapter and generic Chapter-page writes at the maintenance cutoff; only the controlled operator remediation path in step 3 may write. Do not expose P04 title-required create/update or title-bearing public metadata against unremediated rows. Record the applied expand version before any remediation. A combined checkout containing both pending P04 migrations is **not** a valid first `db:migrate:deploy` target for an unremediated populated database.
3. **Remediate and prove:** Authorized operators supply genuine editorial titles and accepted media associations on the expanded schema, or explicitly use the supported publication lifecycle through a controlled authorized path to change state where content cannot be repaired. The operator procedure must preserve Chapter/page/reference/event identity and record each decision and final row state; direct data repair, if needed before the new authoring API is enabled, must be bounded, audited, and transactionally rehearsed on the restored copy. Re-run the inventory and validate zero rows violating final title, position, reference, or published-readiness checks. If any decision or row remains unresolved, stop; do not fabricate values, silently hide or unpublish a published Chapter, or advance the enforcement migration.
4. **Enforce and cut over:** Only after the zero-violation result, package/apply the separate new enforcement migration that makes title non-null and enforces active-page and published structural readiness at commit. Deploy shared contracts, API, and web in the coordinated cutover; keep old editorial writes blocked until all producers and consumers agree. Verify the applied migration versions, OpenAPI, final database constraints/rows/history, and both public and private projections before reopening writes. A fresh empty installation may apply both migrations in order; a populated upgrade may not skip the expand/remediation gate. No `db push`, reset, or down migration in production.
5. **Failure/recovery:** If expand fails, inspect migration state and use the last compatible service while retaining any applied forward schema; do not reverse an applied migration by editing its file. If remediation or enforcement fails, keep writes/cutover blocked, preserve the expanded data and prior public contract, correct forward, and re-run the inventory before another attempt. If cutover fails after new writes, retain the forward schema and roll forward with a corrective migration; restoring a backup requires a coordinated database/media snapshot, publication-event verification, and explicit data-loss acceptance. Rehearse backup, media restore, failed stage, and rollback/roll-forward on a disposable populated copy before release claims. P04 planning does not assert these rehearsals occurred.
